# Shadow-mask passes and the composite clear: fewer full-screen round trips (2026-10-15)

Goal: the M3 Pro at 2× and 60 FPS, faithfully. Branch `agent-2/20261015-0846-m3-bandwidth` (from `macos` e4210c3).
Evidence: `out/validation/m3bw-20261014/` in slot agent-2 (KEEP): `passrank.py` / `table.py` (per-pass ranking),
`rank-*.txt`, `run.sh`, `parity2.sh`, `dumpcheck.py`, one folder per run, `parity-*.txt`.

## 1. Where the M3 spends its 2× frame

Data: the "2x uncapped, pass trace" run of the maintainer's M3 kit (`benchmark-results/M3-Pro-Mac15_6-2026-10-14_11-58`,
build 51757bd, sweep frames 401–949). It is compared with M5 Max Bower runs on the same footprint configuration at
2× and 3× (`docs/ssmask-20261014.md`, `FABLE2_EFFECTS_FOOTPRINT_VARIANT=0`).

- Per pass: marginal busy µs per frame. Host keys are normalised to guest size, so 2× and 3× rows line up.
- The whole frame is 2.74× slower on the M3 than on the M5.
- Passes with a larger M3/M5 ratio are the ones that scale with memory traffic, not ALU.

| Pass | M3 2× µs | M5 2× | M3/M5 | M5 3×/2× |
|---|---|---|---|---|
| main colour pass (2×MSAA HDR) | 6616 | 2379 | 2.78 | 1.35 |
| screen-space shadow mask | 1879 | 474 | 3.97 | 2.14 |
| depth prepass | 1082 | 284 | 3.81 | 1.32 |
| quarter-res post | 1014 | 400 | 2.53 | 2.77 |
| final composite + UI | 931 | 246 | 3.78 | 3.29 |
| main-depth resolve | 528 | 156 | 3.39 | 1.98 |
| **P8a self-depth transfer pass** | 440 | 95 | **4.61** | 2.03 |
| final frontbuffer resolve (compute) | 426 | 109 | 3.91 | 2.19 |
| **frame-start composite clear pass** | 184 | 56 | 3.25 | 2.22 |
| **P8b stencil-only clear pass** | 179 | 37 | **4.88** | 2.50 |

The three bold passes do almost no shading. Each one loads and/or stores a full-screen target at 2×: D32S8
2240×1440 or RGB10A2 2560×1440, about 15–16 MB per load or store.

This change removes P8b's pass and the frame-start clear by default. With `FABLE2_SSM_MERGE=1` it also removes P8a's
pass and the mask pass's depth load.

## 2. Changes

Each has an env switch and a Dev Launcher toggle (Fixes → Render targets). The stencil fold and the composite clear
are default on. The merge is opt-in (section 3).

### `FABLE2_SSM_MERGE=1` (opt-in): P8a's transfer inside the shadow-mask pass

**Before.** The stencil-only alias clear P8a (`docs/main-depth-20261014.md`) ran its own pass. That pass did three
things:
- the K1 host-depth store;
- a transfer of main depth [1008,1260) into `630t <14t> 1× D24S8`, with P7's depth-word band carried;
- a deferred stencil clear, which the shadow-mask pass then drew first.

The shadow-mask pass then loaded the whole depth/stencil target again.

**Now.** `TryStencilOnlyAliasClear` changes ownership as before but queues its GPU work (`queued_stencil_alias_`). The
next `Update` that binds the variant as depth, with no transfers of its own into it or out of it, draws all of it
inside that pass, in the old order:
1. the carried clear;
2. the transfer quads (K1 store before the pass, as for any in-pass self-depth transfer);
3. the stencil clear, in a new post-transfer slot (`pending_draw_pass_post_clear_`).

The carried band (rows 0–432) and the transfer (rows 432–720) cover every row of the target. So the depth/stencil
load is DontCare (`StencilAliasCoversTarget`), and the stencil load is Clear 0 before the quads write it.

**Exactness.**
- The same shaders write the same values in the same order. Only the pass boundaries move.
- The carried clear is checked at queue time to be disjoint from every transfer rectangle. That is why the K1
  store of those rectangles does not need it first.
- Any other cache call while the work is queued first does today's standalone work (`FlushQueuedStencilAlias`).
  That covers alias clears, resolves, an `Update` that does not qualify, the frame start, dumps and snapshots.
  The tile-resolve precheck refuses while work is queued.

### `FABLE2_SSM_STENCIL_FOLD`: P8b's dead stencil reset

P8b resets the variant's stencil to 0 after the mask. Its only reader is the main colour pass's transfers, which move
every tile of `630t` to main depth and to the HDR target. The reset was flushed as a pass of its own because those
transfers read the stencil.

Now, when an update's transfers read a 1× depth source whose only pending clear is a whole-target stencil-only clear,
and after the update the source owns none of those tiles:
- those transfers read the stencil from a constant R8Uint texture holding the cleared byte;
- the clear is dropped (`FoldDeadStencilClears`).

Why that is safe:
- No later transfer reads this target's stencil for those tiles: a tile is always read from its current owner.
- Host depth reads only depth, which a stencil-only clear never changes.

### `FABLE2_CLEAR_CONST_SOURCE`: the composite's resolve clear becomes its pass's load action

The final composite (`0t <16t> 1× k_2_10_10_10`, 2560×1440 at 2×) is copied to the frontbuffer with a resolve that
also clears it. That clear was deferred, then flushed as a full-screen pass at the next frame's first transfer that
read the composite target's tiles. The composite pass then loaded the target again.

Now, a transfer whose source colour target has a single pending whole-target clear reads a constant texture instead
(`TryClearConstSource`):
- The constant texture has the same format and size and holds exactly that clear. It is made once per (format, size,
  value) with the same clear load action the in-pass whole-target clear already uses (`ClearValueAsLoadAction`:
  formats whose clear is exact both ways).
- At most 4 such textures exist; they are never evicted.
- The clear stays deferred until the composite pass binds the target again. There it becomes the pass's load
  action, followed by the in-pass transfers that bring back the tiles other targets claimed.

The frame-start pass and the composite's load are gone; the pass key is now `c0:90/2560x1440x1/CS`.

**Bug fixed in the existing load-action path.**
- `ApplyClearLoadActions` tested the stencil-only flag (bit 63) on colour clears too.
- 32bpp resolve clear values repeat the word in both halves, so any colour clear with its top bit set (`C0000000`
  here) was taken for a depth stencil-only clear. It was drawn as a quad after a load instead of becoming a load
  action.
- The flag now applies to depth only. `FABLE2_CLEAR_CONST_SOURCE=0` keeps the old behaviour.

### Not done: the final resolve as an in-pass tile resolve

It is not exact. A composite draw (PS `686DE15F`, `T13 = 0x1ECFF000`) samples the frontbuffer that the resolve
writes, so a tile function writing it inside the pass would race other tiles' reads. The tile-resolve gate already
refuses it (`fused-target-sampled`). It stays on compute.

## 3. Results

**Measurement setup**
- M5 Max, Bower Lake `hero1-dog-live_2026-10-11_11-20-20`, pinned agent cache `aecf9e7e7e5b85c0@2`.
- Uncapped, `FABLE2_GPU_TIME_TRACE=1`, arms alternated.
- "Off" sets all three switches to 0.
- Every run: verdict ok, 0 AV, contention 0.

**Per pass at 2× (µs/frame, marginal busy)**

| Change | Pass removed | What is added | Net |
|---|---|---|---|
| Stencil fold | P8b clear pass, 41 | nothing measurable | −41 |
| Composite clear | frame-start clear pass, 62–74 | nothing measurable; the composite pass is unchanged (275–283) | about −65 |
| Merge (opt-in) | self-depth pass, 99–109 | mask pass +50–75 (the in-pass transfer quads); K1 store and texture uploads that the old pass overlapped for free, +30 to +110 | about 0 to +0.1 ms |

At 3×:
- the removed passes are 214, 138 and 107 µs;
- the mask pass grows by 120–170 µs with the merge on.

**GPU ms/frame, headings8-long**

| Arm | 2× runs | 2× mean | 3× runs | 3× mean |
|---|---|---|---|---|
| all off | 7.307, 7.310, 7.252 | 7.29 | 12.279, 12.289 | 12.28 |
| fold + composite clear (**new defaults**) | 7.268, 7.236 | **7.25 (−0.04)** | 11.078 (pair, rebased on 20637bc; its off arm 11.014) | +0.06, within noise; FPS 88.6 → 89.1 |
| all three on | 7.332, 7.502, 7.336, 7.311, 7.390 | 7.37 (+0.08) | 12.325, 12.272 | 12.30 |

At 3× the new defaults remove 215 µs of passes per frame (frame-start clear 127, P8b 88; busy 11.108 → 11.084 ms; slot agent-5 `R3-*`). headings8 at 3× (`I3-*`, one run each) gave the same picture within ±0.25 ms per-boot noise. At 1× (`F1-*`), 4.743 off vs 4.756 on.

**Why the merge is opt-in.** It is exact (dump check below), and on the M5 it removes about 100 µs of pass work. But
the old pass ran concurrently with the frame's resolved-texture uploads. In the merged order those uploads are
exposed, so the M5's total GPU time rises by about 0.1 ms at 2×. `FABLE2_SSM_MERGE=1` turns it on, and the Dev
Launcher toggle is off by default. It needs an M3 (or M1) A/B before it can become a default.

**M3 Pro estimate at 2× (not measured)**
- The removed passes measured on the M3 kit (51757bd, scaled to today's code) are:
  - P8b pass: 0.17 ms;
  - frame-start composite clear: 0.15 ms.
- The composite pass no longer loads its 2560×1440 RGB10A2 target: 14.7 MB per frame, about 0.1 ms at the M3's
  effective bandwidth.
- **New defaults: about −0.3 to −0.4 ms.** That takes the post-footprint estimate of 17.4–18.2 ms to about
  17.0–17.9 ms.
- **Merge (opt-in):**
  - It removes the 0.41 ms self-depth pass and the mask pass's 16.5 MB depth load.
  - It adds the in-pass quads (~0.15–0.2 ms at the M3's ALU ratio) and loses the upload overlap.
  - Estimate: −0.1 to −0.3 ms, uncertain. Worth one run of the maintainer's kit with `FABLE2_SSM_MERGE=1`.

## Switches and counters

| Switch | Default | Meaning |
|---|---|---|
| `FABLE2_SSM_MERGE=1` | off | P8a's transfer, carried clear and stencil clear inside the shadow-mask pass, DontCare depth load (opt-in) |
| `FABLE2_SSM_STENCIL_FOLD=0` | on | P8b's stencil reset drawn as its own pass |
| `FABLE2_CLEAR_CONST_SOURCE=0` | on | Pending whole-target colour clears flushed before transfers read them; colour clears with bit 63 set drawn as quads |
| `FABLE2_MAIN_DEPTH_DUMP_SKIP=<bits>` | 0 | Diagnostic: skip dump checkpoints (2 = b, which would flush the queued P8a work) |

Counters (frame CSV, `FABLE2_GPU_TIME_TRACE=1`):
- `tr_n_ssm_merged`: P8a work drawn in the next pass;
- `tr_n_ssm_flushed`: P8a work done the standalone way;
- `tr_n_ssm_dontcare`: mask passes with a DontCare depth load;
- `tr_n_ssm_folded`: dead stencil clears dropped;
- `tr_n_clr_const`: transfer sources read from a constant clear texture.

Bower 2×, per frame: folded 1, clr_const 2 (defaults). With the merge on: merged 1, flushed 0, dontcare 1.

Files:
- `backends/metal/port/rex/graphics/metal/metal_render_target_cache.cc/.h`: queue, flush, post-transfer slot,
  coverage check, stencil fold, constant textures, load-action flag fix;
- `metal_tile_resolve.cc`: precheck;
- `metal_command_processor.cc`: counters, dump skip;
- `metal_shared_memory.h`: counters;
- `tools/macos/Shared/LaunchSettings.swift`: toggles.
