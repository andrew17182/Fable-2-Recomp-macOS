# Bug patterns and triage playbook

Check this first when a playtest bug comes in. It lists the bug classes found and fixed so far, where the
fixes live, and the tools that diagnosed them. The open findings of the pattern-based code review are in
the 2026-10-07 code review, ranked; check whether the new bug matches one of them.

## Triage order

1. **Symptom → table below.** Match what the maintainer describes (flash, missing effect, slow load, crash, stutter)
   against the "Symptoms" column, then check the open findings in the 2026-10-07 code review.
2. **Read the reporter's session evidence before reproducing**: `python3 tools/f2diag.py dumps <session>`, then
   `f2diag report <session>` on the newest/relevant dump and `f2diag digest <session>` (first occurrence of every
   warning/error). Then the log, `out/dev-sessions/<id>/test-state/logs/fable_2.log`: grep for
   `persistent miss`, `skipping`, `Failed to create`, `materializeAll`, `[crash-diag]`, `AV`, and `writeback.jsonl`
   events. Many bugs show here without a live run.
3. **Reproduce lean.** Use 1–2 background runs (`tools/fable2_dev_session.py launch ... --test-control --target-slot none`)
   with the existing harnesses (below). Never discard the first launch after a rebuild. Prefer a direct counter
   or trace over repeated statistical runs.
4. **Switch toggles before writing code.** Every fix has a launcher toggle or env var, so try the A/B first.

## Tools and harnesses

- **Flight recorder first** (always on since 2026-10-08, `FABLE2_TRACE=off` disables; switch reference in
  `docs/telemetry-design-20261008.md` §15). Every session has `<session>/test-state/logs/trace/` (title-mode runs:
  `logs/trace/` in the state folder): `session.json` (build, env, tags, hooks that never fired),
  `log-digest.jsonl` (first occurrence + count of every warning/error, survives log rotation) and
  `dumps/NNN-<reason>/` written automatically on a >1 s frame gap outside a level load, a 3 s hang, the first
  guest AV, an AV storm, a GPU timeout, a `persistent miss`, a `[crash-diag]` or pipeline-failure line, and on
  close (`exit`). Each dump has all-thread guest stacks (3 snapshots, no suspension), the event rings
  (frames, waits ≥ 2 ms with stacks, level loads, file opens, log lines, tags, 100 Hz all-thread stack samples).

  stacks, top sampler stacks in the 2 s before, timeline, digest rows near it); `dumps`, `timeline`, `gaps`,
  `threads` (WORK/SPIN/WAIT per thread, host CPU, waits by call site), `stacks`, `phases`, `digest`,
  `export` (Perfetto JSON), `sym`. Triage step 2 above now starts with `f2diag report` on the newest dump and
  `f2diag digest`.

  (`--fps`, `--env`, `--game-arg=--cvar=v`, `--cache-from DIR`, `--cpu`); library in `tools/f2diag/run.py`; artifact
  detectors `f2diag images dark|blue <sweep result.json>` (`tools/f2diag/images.py`, no PIL/numpy needed); frame
  pacing `tools/f2diag/pacing.py`; per-thread CPU without attaching `tools/f2diag/threadcpu.py`.

## Lessons

- Machine speed drifts between batches by more than small effects (gpucmd-cpu round 4, 2026-10-14: a batch ran ~6% faster in town 2× than one 20 minutes earlier, in both arms). Compare only arms interleaved in the same window; for two builds, swap APFS clones of `out/build` between runs (`out/validation/gpucmd4-20261014/abz.sh`).
- A parity difference confined to one object, present in every frame of a run and absent from others, may be a per-boot game state: bisect with several runs per arm before blaming the change (gpucmd-cpu, 2026-10-14: the Bower save boots with the tree root by the camp fire lit one of two ways, ~25% per run, independent of any switch; compare runs in the same state).
- Sampled captures (~17–20/s) miss single-frame glitches only partly. A per-frame counter or per-draw dump settles the cause faster than more runs.
- "Clears up after a while" means first-use or setup work. "Only near X" means find X's draws in a dump.
- A fix that makes skipped GPU work run again can cost frame time (CR-03: about 16% uncapped, nothing at 60 FPS). Measure uncapped and at 60 FPS.
- Before blaming the new GPU work itself, check the synchronisation it triggers: CR-03's cost was the barrier storm of pattern 18, not the draws (2026-10-08).
- Compare scales in linear light, region by region. A perceived saturation loss between 1× and 2× (2026-10-10, save 13-27-55) turned out to be finer texture detail plus comparison sheets box-downscaled in gamma space. Per-region linear-light statistics matched within 1% (saturation, chroma, hue within 1°), in both guest and presented-drawable captures. The presenter path does not depend on scale (`out/validation/hires-fps-20261010/save132755/colorstats.py`).
- Measure redundancy before building a skip. A content-generation counter for resolves (2026-10-10, `docs/resolution-scale.md` §11) showed 0 redundant copies: the game redraws every target every frame. The skip would never have fired.
- Before calling a perf number a regression, check the CONTENTION line (`f2diag report|dumps|run`, result.json
  `perf_comparable`): another game instance (the player's playtest copy) shares the GPU and CPU (2026-10-10).
- Check every renderer setting A/B, but large run-to-run variance (2–21 flashes per run) means a single run proves little. A mechanism counter is the evidence.
