## 1. "No load" check followed by a load (`FABLE2_LOAD_CHECK_EXACT`, default on)

### Cause: a race with guest CPU writes, not a gap in the predicate

Round 3 found that `MayRequestTexturesLoadData` sometimes answers "no load" and `RequestTextures` then loads a texture
anyway (43 per town 2× spin, 92 per area run). `FABLE2_LOAD_CHECK_TRACE=1` (new, diagnostic) logs each such load. For
each one it records:
- the texture key and its outdated flags;
- the call path (`backtrace` + `dladdr`);
- a fresh check run just before the request;
- the load-check state (epoch, scaled-resolve generation, in-sync bits) at the check and after the request.

What the trace showed (town 2× spin, 19 requests with 21 loads):

- **The textures are ones the game rewrites from the CPU.** 16 of the 21 loads were one 16×16 cube map at
  `1F48B000` (k_8_8_8_8, base outdated). The rest were two 16×16 2D textures at `1A540000` / `1A546000` (3 loads)
  and a 64×1 1D texture (1). The 21st was a queued draw's planned load (see the side effect below).
- **The epoch went up by exactly 1 during the request** in all 15 requests that reused the check, which means one
  watch callback ran. The callback runs on the guest thread that faulted on the write, under the global lock. The
  4 rechecked requests had +5 to +7.
  - In 9 of the 19 requests the fresh check just before the request already said "load": the write landed between
    the check and the request.
  - In the other 10 it still said "no load": the write landed during the request.
- **The predicate itself is exact:**
  - the round-3 verify (`FABLE2_DRAW_PREP_LITE2_VERIFY=1`) has 0 mismatches;
  - after the fix, no load ever had to be kept as a "gap" (below).
- **A side effect:** such a load is not in an upload batch, so it ends the open render encoder. That flushes the
  prepared-draw queue, which runs the queued draws' own planned loads. Those loads were also counted in the
  "outside the batch" delta (one trace line: `ExecuteTextureMaterialization` ← `FlushPreparedDrawQueue` ←
  `EndRenderEncoder`).

### Fix: the request follows its check

- **The watch callback records an epoch.** `TextureCache::WatchCallback` already bumps the load-check epoch under
  the global lock. It now also stores the new epoch value on the texture (`cpu_invalidated_epoch_`). After a GPU
  invalidation (resolve or memexport, `invalidated_by_gpu`) it stores 0 instead.
- **The caller passes the check's epoch.** When the check said "no load", the caller sets
  `request_defer_after_epoch_` to the epoch it read before the check. In the round-3 reuse path that is the
  snapshot's epoch; after a recheck, the epoch read just before the recheck. The plain `RequestTextures` path
  (`FABLE2_DRAW_PREP_LITE2=0`) does the same.
- **`RequestTextures` sorts the loads under the global lock:**
  - **deferred:** a texture that is outdated *only because of a CPU write after that epoch* is left outdated;
  - **gap:** any other outdated texture is still loaded, as before, and counted as a gap (a load the check missed).
  The binding itself is updated exactly as before.
- **Effect:**
  - **This draw** samples the data from before the write. That is the order "the GPU fetched before the CPU write
    landed", which the guest allows because the write and the draw are not ordered.
  - **The next draw that uses the texture** sees it outdated, so its check says "load" and the load runs in that
    draw's upload batch or pre-commit plan.
  - **No load runs outside the batch any more.**
- **Exactness rule:**
  - a CPU write that is ordered before the draw is never deferred;
  - anything the check could have seen still loads.

### Faithfulness (raised by main): why no draw can see stale data it should not

**(b) A CPU write that lands before the check is never deferred.**
- The callback sets the outdated flag, then bumps the epoch (release), both under the global lock. The caller reads
  the epoch (acquire) before running the check.
- If the write's epoch is ≤ the check's epoch, the bump happened before that read, so the flag was visible to the
  check. The check therefore said "load", and the no-load path never runs.
- So a deferral needs epoch > check epoch, which is exactly the deferral condition. It is read under the lock, so
  the flag and the epoch are consistent.
- A guest write ordered before the draw packet always lands before the check:
  - the fault handler runs the callback before the store completes;
  - the store completes before the guest advances the ring write pointer;
  - the command processor reads the draw packet only after that.
- Any pre-check write the check missed would be loaded and counted as a gap. Gaps were 0 in every run.

**(a) The deferred load runs before any later draw samples the texture.**
- A deferred texture keeps its outdated flag, which only a load clears.
- Its binding is in sync, so `GetUsedTextureRequestWorkMask` marks the slot of any later draw that uses it as work.
  The check (`is_texture_outdated`) then says "load", and the draw loads it:
  - in its upload batch; or
  - through its materialization plan, which runs in the queue flush before that draw is encoded.
- The same holds in each case main raised:
  - **Across a frame boundary:** `ResetTextureBindings` makes the slot out of sync. The key-changed path finds the
    same texture, and `key_may_need_load` sees it outdated.
  - **After a resolve or memexport touches the range:** the GPU invalidation only sets the flag again (and stores
    epoch 0, which makes a later load a gap rather than a deferral).
  - **After a scaled-resolve change:** the host key moves to another texture, which is new or outdated itself.
- **Verify mode `FABLE2_LOAD_CHECK_EXACT_VERIFY=1`** tracks every deferred texture until a later request finds it
  loaded:
  - if a later draw uses it while it is still outdated, with no newer CPU write and no planned load, that is a
    **violation** (counted, the first 16 logged with slot, frames and GPU-invalidation state);
  - it also counts loads in a later frame and after a GPU invalidation.
- **Negative control** `FABLE2_LOAD_CHECK_EXACT_VERIFY=2`: the same check, but a draw's materialization plan is not
  credited. It must report violations, and it does: **241** in a town 2× spin.

## 2. Inline `rex::bit_scan_forward` (SDK patch `patches/sdk/bit-scan-inline.patch`)

- **Change:**
  - `rex/math.h` defines the `uint32_t` / `uint64_t` overloads inline (`__builtin_ffs` / `__builtin_ffsll`,
    exactly the old bodies, including `*out = UINT32_MAX` for 0) on clang/gcc;
  - `math_gcc.cpp` drops its out-of-line copies; MSVC keeps the declarations.
- **The patch goes to both SDK trees, and both must see the same header:**
  - the runtime tree, in `SDK_BEHAVIOUR_PATCHES` of `tools/build_sdk_from_source.py`;
  - the Metal plugin's `sdk-source`, the 6th entry of `PATCHED_TREES` in `tools/build_macos_metal.py`.
- **Check:** `nm` shows the export is gone from `librexruntime.dylib` and that neither `librexgpu-metal.dylib` nor
  `fable_2` imports it.
- **Rebuild cost (once per checkout, including every slot and main after the merge):**
  - **452 s wall** for the first build with the patch. It has three parts:
    - the full SDK from source (144 s: any change to an SDK patch re-extracts and rebuilds it);
    - 333 game units, because the SDK root changed;
    - 67 Metal backend units, because `sdk-source` was re-extracted.
  - The build without the patch, for the A/B, took 279 s (SDK 104 s).
- **Not in the agent shader-cache key:** it has no shader hunks.

## 3. Draws per flush and flushes per frame: encoder worker go/no-go

Measured with `--metal_backend_telemetry=true --metal_backend_telemetry_interval=60`. The counters are per 60-frame
block, and the first two blocks are skipped (`flushstats.py`, `fs-*/flushstats.txt`; spin5, 540 frames each).

| | Town 1× | Town 2× | Bower 2× |
|---|---|---|---|
| Draws per frame | 4518 | 4525 | 2531 |
| Through the prepared-draw queue | 1904 (42%) | 1899 (42%) | 1067 (42%) |
| Encoded directly (queue rejects; mostly `resident_no_active_queue`) | 2215 | 2226 | 975 |
| Queue flushes per frame | 60.8 | 62.0 | 57.3 |
| Draws per flush | 31.3 | 30.6 | 18.6 |
| Single-draw flushes | 30% | 26% | 52% |
| Render passes per frame | 53.7 | 57.1 | 79.0 |
| Draws per pass | 84 | 79 | 32 |
| Resolve boundaries per frame (`resolve_needs_boundary`) | 45 | 45 | 81 |

Flush reasons in town (per 60 frames): queue budget (64 draws) 1270–1350, copy 1180–1220, RT key mismatch 930,
RT update 240–260. Command-buffer ends: ~10.5 per frame.

**Cost model.**
- In town 2× the thread spends ~10.1 ms on ~4500 draws, ~2.2 µs per draw. Round 3's profile puts ~25% of the thread
  in encoding (`EncodePreparedDraw`), so ~0.55 µs per draw is encoding and ~1.65 µs is preparation.
- **The ceiling:** a worker that encodes while the command processor prepares hides at most the encode quarter:
  ~2.5 ms/frame on the M5 Max town 2×, ~4–5 ms on a base M1 by the round-3 ratio.
- **The drains:**
  - Every non-draw encoder use needs one: pass ends (54–79), resolve boundaries (45–81), command-buffer ends
    (~10), transfers and uploads (~10). That is about **110–180 drains per frame**.
  - So the segments a worker could overlap average ~25–40 draws in town and ~15 in Bower.
  - The worker is faster than the producer (0.55 vs 1.65 µs per draw), so at a drain it lags by about one draw.
  - The drain cost is the hand-off itself. With a spinning worker that is near zero, but it burns a P-core for the
    whole frame. On a base M1 (4 P-cores, with the guest threads and this thread already ~1.9 cores) that is a
    real cost.
  - With a sleeping worker, each wake costs ~10–30 µs. 110–180 wakes a frame is 1–5 ms, which cancels the gain.
- **Directly encoded draws:** half the draws bypass the queue today (`resident_no_active_queue`). The worker would
  have to take those too, or the segments become ~15–20 draws long.

**Go/no-go: no-go for a prototype in this round; a conditional go as its own project.**
- **The gain is real but bounded:** 1–1.5 ms after overheads on M5 town 2×, 10–15% of the thread. It is largest
  on the Macs that need it most (base M1 at 1×).
- **It needs a spinning (or hybrid spin-then-park) hand-off** to survive 110–180 drains a frame, so it costs a
  P-core.
- **It is not containable behind a switch here.** `EncodePreparedDraw` reads and writes:
  - the encoder binding caches;
  - resource-use and residency tables;
  - pending shared-memory write fences;
  - tex-rename orphan state;
  - upload batches;
  - telemetry;
  - the current render encoder.

  The pass, resolve, transfer and upload code would all have to route through the same ordered stream or drain
  first.
- **Cheaper steps to take first:**
  - fewer passes and resolve boundaries in Bower (32 draws per pass);
  - letting the 42% → ~100% of draws flow through one queue.

  Both lengthen the segments the worker would overlap, and both help without a second thread.

| Switch | Default | Meaning |
|---|---|---|
| `FABLE2_LOAD_CHECK_EXACT=0` | **on** | A request after a "no load" check loads CPU-written textures again (old behaviour). `=2`: diagnostic, filter runs but defers nothing. Dev Launcher → Performance → "Texture loads follow the draw's check" |
