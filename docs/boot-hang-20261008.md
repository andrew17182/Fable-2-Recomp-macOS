# Intermittent boot hang before the title (2026-10-08)

Status: root cause found (SDK ring-buffer re-init replays GPU packets). **Fixed** (`FABLE2_RING_REINIT_FIX`, default on;
section 6): skew 0/70 boots with the fix (was ~95%), 0 hangs in 70 boots.
Branch `feature/macos-playtest`, HEAD f945b16. Restore point: `../restore-points/2026-10-08-boot-hang-before.patch`
(empty; the tree was clean).

## Symptom

Session `out/dev-sessions/20261008-100209-3d750d45` (`tbE2-off-60`: 60 FPS, `FABLE2_TEXTURE_PRECOMMIT=0`, boot of
`hero1-dog-live_2026-10-07_14-45-08`, binary built at 09:55). The guest stopped swapping at frame 9, about 1.0 s after
recorder start, before the title screen. There are no `[title-fast]` or `[boot-save]` lines. The run sat for 47 s,
and only `001-frame_gap` (1 s) and `002-exit` dumps were written. No `hang` dump fired (recorder bug 1 below).
The identical next run (`100426-246b9a37`) was fine.

## 1. What GameThread waits for

Stack: `82CBD0A8 YieldAndCheckThreshold < 82B69670 (82B69488) < 8236D128 (8236D0A8) < 8237866C (823784A0) < 822F48CC < 822EAA5C`.

- **8236D0A8** is the loading-screen frame on GameThread. It increments the counter 0x83360198 and calls
  82A3BC58 (render, takes the critical section). If byte `[obj+0]` is 0 (nobody else presented), it presents
  itself by calling 82B69488.
- **82B69488 = Present.** In order: 82B9C7F8(device), then `InsertCallback(82B89A78, arg 0x834A5CFC)` via 821F5F20
  (D3D: scratch-register write + PM4_INTERRUPT), then a non-atomic `++*(u32*)0x83496F44` (presents). Then the
  **frame throttle** at 82B6966C:

  ```
  do { NtYieldExecution(); s = Stats(82B89960); } while (s.callbacks - s.presents > 1);   // signed
  ```

  `s.presents` = `*0x83496F44`. `s.callbacks` = `stats[idx].count`, with the stats at 0x83491BD0 (2 × 24 bytes,
  count at +16) and idx at 0x83496F48. Then come the swap (82B9CD68) and the profiler scope.
- **82B89A78** is the GPU frame callback. The guest GPU interrupt handler 82B9B8D8 (source 1) runs it on the
  GPU Commands thread. It writes the other stats buffer with `count = old + 1` and flips idx. 82B89A78 is the
  only writer of the count; Present (and the static initialiser 8328BC98) is the only writer of the presents
  counter. Only Present inserts 82B89A78.

**So the "flag" polled is `callbacks - presents`, and the signaller is the GPU frame-callback interrupt.** Normally
callbacks ≤ presents (exit dumps: callbacks = presents − 1…+1), and the loop is never entered. Nothing inside the
loop changes either value, and callbacks only grow. **Once the loop is entered with a skew of 2 or more, it never
exits** unless another thread presents. In the hung run the 3D Engine (the other presenter) sat in its idle wait
(`sub_8236C360`), so the hang was permanent. A solo presenter checks with its own callback still queued (lag 1), so
the hang needs **3 or more extra frame callbacks** (2 if the check is delayed by a vblank).

Other threads in the dump: VFS Request Finalizer/Manager idle; the boot loader (Permanent Bank Mounter, guest
tid 22) had finished and exited by 2.0 s; the job workers were idle (`ByteValueCheck` delay); the Texture Streamer was idle;
the D3D keep-alive thread XThread1A703 (82B9F598) timed out every 30 ms; the GPU command processor was idle.

## 2. Why the count runs ahead (evidence)

Instrumentation (trace-only, section 5): a recorder watch logs `[trace] frame-throttle skew N` whenever
callbacks > presents, and `FABLE2_THROTTLE_TRACE=1` adds wrappers that log Present, InsertCallback(82B89A78), the
frame callback, the GPU interrupt handler, the pre-swap call and the ring init imports.

- **Callbacks exceed presents in almost every boot** at guest frames 6–9: 19/20 (`bh-skew`), 4/4 at 30 FPS,
  4/4 uncapped, every traced boot. The extra is always exactly 1 in these runs.
- **Not a lost `++presents` race.** In a traced boot (`20261008-103701-b13af93d`), 4 inserts by the 3D Engine
  (`insert frame callback #0–#3`) were followed by 5 frame-callback interrupts. The 5th came as a full
  swap-callback (82B9C648) + frame-callback (82B89A78) interrupt pair with no Present or insert anywhere.
- **The ring is re-initialised while it holds commands.** The guest calls `VdInitializeRingBuffer` three times
  in every boot:

  ```
  GameThread  VdInitializeRingBuffer ptr=1FC9D000 size_log2=12   (+ RPtrWriteBack 1FA9C03C)
  GameThread  VdInitializeRingBuffer ptr=1FC85000 size_log2=14   (+ RPtrWriteBack 1FC8403C)
              pre-swap #0 on GameThread (82B68D18), interrupt 82B9C648, ring read index 5 .. 0xF
  3D Engine   VdInitializeRingBuffer ptr=1FC85000 size_log2=14   (same ring, ~40 ms later)
              interrupt 82B9C648 at once, presents=0   <- stale packets executing
  ```

- **SDK code** (`ReXGlue-SDK-Source/src/graphics/command_processor.cpp`):
  `InitializeRingBuffer()` sets `read_ptr_index_ = 0` (plus base and size) **on the calling guest thread**. It leaves
  `write_ptr_index_` at its old value (0xF here) and does not synchronise with the GPU Commands worker. The worker
  loop (`WorkerThreadMain`) runs `ExecutePrimaryBuffer(read, write)` whenever read ≠ write. So it **replays
  ring[0, oldWPTR)**. By then the 3D Engine is already writing its first two presents into that same range (both
  presents were issued in the same millisecond as the re-init), and every group the replay reaches runs again when
  the guest advances WPTR. Each duplicated present group runs 82B89A78 one extra time. If the guest's new WPTR is
  below the replay end, the worker also wraps through the whole 128 KB ring (stale memory) back to the new WPTR.
- None of our boot features change the skew. With each switch at 0, 5 boots each, the skew stayed 1 in every boot:
  `FABLE2_RING_WAIT`, `TURBO_WAIT_FIX`, `GAME_TICK_SLEEP`, `WORKER0_DRAIN`, `BOOT_LOADER_KICK`, `FAST_CONTENT_IO`,
  `STREAM_BUDGET`, `SAVE_FAST_MOUNT`, `TITLE_FAST`. **It is pre-existing SDK behaviour.** It is not the boot-loader
  drain (DrainPending), the stream budget, CR-01, save fast mount, the turbo wait fix, the tick sleep, ring wait, or
  guest memory ordering.

## 3. Repro rate

- Hangs: **0 / 85** boots on the instrumented build (15 + 40 normal, 30 with all 18 cores busy) plus 0 / 55 more
  in the bisect and trace runs. Across `out/dev-sessions` (135 sessions) the 10:02 run is the only boot-save boot
  that never reached the title. **About 1 in 200+ boots.** A direct hang bisect would need hundreds of boots per switch, so
  the skew (≈95% of boots) served as the proxy.
- The precursor (skew 1) is near-deterministic. The hang needs the race to duplicate more groups. That happens when
  more new present groups land in [0, oldWPTR) before the replay reaches them, or when the replay's wrap re-runs
  them. In the hung run GameThread presented alone for 9+ frames.

**Evidence vs inference.** Evidence: the throttle semantics (disassembly + counter peeks), callbacks > presents
in ~95% of boots, a frame callback with no insert, the third ring init on the same ring and the immediate stale
interrupt, the SDK code, and switches with no effect. Inference: that the 10:02 hang had ≥3 duplicated groups (that
run predates the counter peeks; the next hang dump will show `callbacks`/`presents` in `guest.txt`).

## 4. Proposed fix (as planned; see section 6 for what was built)

**Ring re-init without replay.** This is a strong `__imp__VdInitializeRingBuffer` override in the executable (same
mechanism as `src/core/fable2_skip_intro.h`; no SDK rebuild), default on, kill switch `FABLE2_RING_REINIT_FIX=0`, with a launcher toggle:

1. Park the worker: `graphics_system->WriteRegister(CP_RB_WPTR, 0xBAADF00D)`. The worker's idle loop already treats
   0xBAADF00D as "no commands" and finishes its current batch.
2. Wait (bounded, ~50 ms) until the read-pointer writeback stops advancing.
3. Forward to the real `VdInitializeRingBuffer` (read index 0).
4. Write `CP_RB_WPTR = 0` so read == write. The guest then writes new packets and its next WPTR normally.

An SDK patch (`patches/sdk/`) that resets `write_ptr_index_` and does the reset on the worker is the cleaner long-term version.
Optional belt-and-braces: a hotfunc guard in Present's throttle that logs and resynchronises `presents` when it
sees callbacks − presents > 1 (it cannot exit by itself).

Risk: low–medium. The fix runs only on ring init (3 times per boot, plus device resets). If the guest wrote WPTR
before our step 4, that WPTR would be lost; the guest writes it later from the same thread, after init returns.
The bounded wait keeps a stuck worker from blocking boot.

Validation:
- Skew proxy: `frame-throttle skew` in 0 of 20 boots (`f2diag run bootloop <label> --n 20`), against ~19/20 now.
- 50-boot hang loop, and with `FABLE2_THROTTLE_TRACE=1` one insert per frame-callback interrupt.
- A normal area load and an F5 save (`f2diag run area|f5`), to check that nothing else depended on the replay.

## 6. Fix (implemented 2026-10-08)

Restore point: `../restore-points/2026-10-09-ring-reinit-before.patch` (+ the untracked files in the matching folder).

### Design

Switch: `FABLE2_RING_REINIT_FIX` (default on; `=0` restores the old behaviour). The env read is cached. It is an
internal fix, so there is no launcher toggle.

- **Executable:** `src/core/hotfunc/gpu/RingReinitFix.cpp` holds a strong `__imp__VdInitializeRingBuffer` (and
  `__imp__VdEnableRingBufferRPtrWriteBack`, trace only). Both forward to the real imports with
  `dlsym(RTLD_NEXT)`. The `FABLE2_THROTTLE_TRACE` logging of these two imports moved here from
  `FrameThrottleTrace.cpp`, because a strong symbol can only be defined once.
- **Metal plugin:** `MetalCommandProcessor::ParkRingForReinit` / `FinishRingReinit`
  (`backends/metal/port/rex/graphics/metal/metal_command_processor.{h,cc}`), exported as the C function
  `fable2_ring_reinit(op, IGraphicsSystem*, timeout_us, out[3])` (`metal_graphics_system.cc`). The executable
  finds it with `dlsym(RTLD_DEFAULT)`, the same pattern as `fable2_ring_progress_*` and `Fable2CheckpointGpu`.

Per `VdInitializeRingBuffer`:

1. **Park** (op 0, guest thread, bounded at 50 ms). Wait until `read_ptr_index_ == write_ptr_index_` (the worker has
   consumed everything submitted), then swap the write index to `0xBAADF00D` with a compare-exchange. On a timeout
   nothing has been changed, the real init runs exactly as before, and a WARN line is logged.
2. **Forward** to the real import: `read_ptr_index_ = 0`, new base and size.
3. **Finish** (op 1): `CP_RB_WPTR` register = 0 and `UpdateWritePointer(0)`, the same two effects as a guest
   MMIO write of WPTR. Now read == write == 0, and the guest's next WPTR write runs only its new packets.

One `[ring-reinit] init #N ... parked (old wptr, read at start, drain wait), total X ms` line is logged per init
(3 per boot).

### Changes from the plan, and why

- **Park and wait run in the plugin, not purely in the executable.** `CommandProcessor` is compiled into
  `librexgpu-metal.dylib` with hidden visibility. Its indices are `protected`, and the plugin builds against the
  *patched* SDK headers, whose layout differs from the headers the executable uses. So the executable cannot
  read `read_ptr_index_`. The alternative drain signal, the RPTR writeback, is guest memory: it is not enabled
  at the first init, and D3D may reset it. (The executable *could* write WPTR itself:
  `MMIOHandler::global_handler()->CheckStore(0x7FC80714, v)` is the guest's own path.)
- **Drain first, then park.** The plan set the sentinel first and then waited. That loses work in one case: if the
  worker is idle-spinning with read ≠ the just-written WPTR but hasn't reloaded WPTR yet, it sees the sentinel and
  never executes [read, WPTR), so the wait would never finish. Waiting for read == write and *then* doing a CAS to
  the sentinel cannot strand commands. read == write means `ExecutePrimaryBuffer` has returned: the worker sets
  `read_ptr_index_` only after the batch ends. With the sentinel in place, the worker cannot start a batch when
  the init sets read to 0. If the guest writes WPTR during the wait, the CAS fails and the wait continues
  toward the new value.
- **Edge cases checked in the SDK source:**
  - WPTR reaches the worker as guest `REX_MM_STORE_U32` → `MMIOHandler::CheckStore` →
    `GraphicsSystem::WriteRegister` (stores the register file and calls `UpdateWritePointer`) → atomic
    `write_ptr_index_` + event.
  - The worker cannot be mid-packet when parked: read == write means the batch has returned.
  - On the first init, read = write = 0, so the park is immediate.
  - The writeback enable comes *after* each init (trace order Init → EnableRPtrWriteBack). The fix does not
    depend on it.
  - Without the plugin export (Vulkan) the fix is inactive and logs that once.
- Rejected simpler options:
  - Resetting WPTR to 0 *before* forwarding makes read (0xF) ≠ write (0), so the worker replays the whole ring.
  - Setting `write_ptr_index_ = read_ptr_index_` after the init still leaves a window where the worker sees
    read 0 ≠ write old.
  - `CallInThread` is unsafe from guest threads (`pending_fns_` is an unlocked `std::queue`).

## 7. SDK fix (2026-10-09, phase B1 of `docs/sdk-from-source.md`)

The runtime and the Metal plugin are now built from source, so the §6 design moved into the SDK:
`patches/sdk/ring-reinit-sync.patch` (runtime tree, i.e. the Vulkan plugin `rexgpu-xenos`), and the same hunks appended
to `backends/metal/sdk-metal.patch` (the Metal plugin compiles `command_processor.cpp` itself). Keep the two in sync.
Changing `sdk-metal.patch` needs `rm -rf out/metal-build/dependencies/sdk-source` before the next build.

- `CommandProcessor::InitializeRingBuffer`: drain (wait for read == write, bounded at 50 ms), park with a
  compare-exchange to `0xBAADF00D`, reset read and base/size, then `CP_RB_WPTR = 0` and `UpdateWritePointer(0)`. On a
  timeout it warns and keeps the old behaviour.
- `WorkerThreadMain` publishes `read_ptr_index_` (atomically) only after the batch's RPTR writeback, and its idle check
  reads the read index between two loads of the write index. This closes a window the §6 workaround still had: the
  worker loads the old write index, the init parks and resets read to 0, and the worker then pairs read 0 with the old
  write index and replays the ring.
- Cvar `gpu_ring_reinit_sync` (default true) switches the synchronisation off.
- The executable override stands down: it asks the plugin (`fable2_ring_reinit` op 2), which reports the cvar. With
  the SDK sync active it only forwards (one log line per boot: `SDK synchronises ring re-init ...; executable fix stands
  down`; with `FABLE2_THROTTLE_TRACE=1` one `forwarded to the SDK sync` line per init).
- A/B without a rebuild: default = SDK fix; `--gpu_ring_reinit_sync=false` = §6 executable workaround;
  `--gpu_ring_reinit_sync=false` with `FABLE2_RING_REINIT_FIX=0` = no fix.
- The plugin is built from source with both runtimes (`FABLE2_SDK_FROM_SOURCE=0` only swaps the runtime), so the SDK
  fix is active with the prebuilt runtime too. The executable workaround remains for a plugin without op 2.
