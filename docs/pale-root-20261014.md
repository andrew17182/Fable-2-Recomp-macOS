# Pale root at Bower Lake (2026-10-14)

**Verdict: game behaviour, not a recomp bug.** The pale root is the game's own distant-LOD texture,
chosen by a per-model size cache in the game's texture streamer. A load-order race decides which camera
view fills the cache first. If the shadow (light) view fills it, the cache stays wrong until the camera
moves. Texture data, fetch constants, the host texture cache and the renderer are all correct. The
investigation tooling is trace-only and off by default.

**Opt-in fix (built 2026-10-14 at the maintainer's request, default off):** `FABLE2_FIX_LOD_SIZE_CACHE=1`, Dev
Launcher and player app Settings → Fixes → "Game bug fixes (changes original behaviour)" → "Fix game
texture-detail cache bug (pale textures)". With it on: 0 of 16 pale; with it off: 5 of 16 pale, the
original game. Section 5 has the details.

Evidence: `out/validation/pale-root-20261014/` (KEEP; slot agent-2).

## Symptom

- **Where:** the default f2diag save `hero1-dog-live_2026-10-11_11-20-20` (Bower Lake, camp fire).
- **What:** a big tree root near the fire (crop x 2300–2560, y 200–460 of the 2560×1440 frame) renders
  pale in some runs: no fine bark detail, flatter shading. The state lasts the whole still run.
- **How often:**
  - It happens at 1× as well as 2×.
  - It happens with every switch set tried: today's gpucmd switches on or off, `FABLE2_STREAM_BUDGET=0`,
    `FABLE2_WORKER0_DRAIN=0`.
- **Classifier** (`paleclass.py`): gradient energy of the root box x 2450–2550, y 335–380 at guest
  frame 346. The two states are clean and bimodal: 7.5 normal, 5.15 pale.
  - The trace-based classifier `traceclass.py` agrees on every run. It reads the root draw's T0 in the
    frame-346 shadow trace.
- **Tally** (light or no tracing):
  - agent-1's 42 earlier runs: 10 pale;
  - this investigation: 26 of 110 pale;
  - pacing A/B: 1 of 8 pale with each switch off.

## 1. The "not resident" skip is unrelated

- **No correlation.** In agent-1's 42 runs (`skip-correlation-agent1.txt`):
  - 3 pale runs never log the skip;
  - most normal runs do log it.
- **What the skipped range is.** `0x1FAB0000`/1024 and `0x1FAB1000`/512 are two 1D lookup textures that
  the main-pass material shaders bind (`skip-range-texture-usage.txt`):
  - T16/T5: 256×1 `k_8_8_8_8`;
  - T17/T4: 64×1 `k_16_16_16_16_EXPAND`.
- **Why it doesn't matter here.** These textures are in 1578 of the 3106 draws of the traced frame and are
  rewritten by the CPU every frame. A skipped load affects one use only, as
  the 2026-10-13 release audit noted.
- **Not the root's texture.** The root's textures are 1024² DXT1 and DXN, so the skipped range does not
  belong to them.

## 2. The game binds different textures for the root

Per-draw trace at frame 346 (`FABLE2_SHADOW_TRACE`). Its lines now also carry each fetch constant's mip
address, mip range and bias, plus the index-buffer base and index count.

| | normal | pale |
|---|---|---|
| Root draws (VS 475EC9F7…, PS 58D3FAAA…, 459 and 1468 strip indices, 3 passes × 2 tiles) | T0 = bark: 1024² DXT1, full mip chain (`mip0-10`) | T0 = `0x17360000` / `0x17BA0000`: 1024² DXT1, `mip0-3` |
| Normal map | 1024² DXN, full mip chain | `0x19300000`: 1024² DXN, `mip0-3` |

- The guest's own fetch constants carry the swap (`root-draws-ps58D3-u-runs.txt`).
- The bark textures are resident and still drawn by other objects in pale runs.
- The `mip0-3` textures are a shared low-resolution atlas. The material slot's UV transform becomes a
  1/8 scale plus an offset (0.125, 0.125, 0.5, 0.375), where a normal slot has the identity.

## 3. Mechanism (guest code)

Traced with `FABLE2_PALE_ROOT_TRACE=1` and `FABLE2_PALE_ROOT_WATCH=1` (`src/core/hotfunc/gpu/PaleRootTrace.cpp`).
Bisection with temporary wrappers found the writer of the material's texture slot.

### Materials

- A material is a 180-byte record.
- Texture slot *i* sits at `+28 + 20 i`: a texture-handle pointer plus a UV transform.
- `mat[i+1]` is the slot's texture-reference object.

### Per-frame update chain

1. The render pass `821ECBA0` calls the object's draw `822DB220`.
2. `822DB220` calls `82A986F8`.
3. `82A986F8` calls `82B197C8(model, distance, …, view)` for every drawn instance of a model.
4. `82B197C8` calls `82A94648(mat, size)` for each material.
5. `82A94648` calls `82A944E8` → `822229F0`, which picks the handle: the full texture at the mip level
   that fits the size, or the atlas proxy (`[texref+100]`) when the wanted level is at or below
   `texref+88`.

### The size cache (`82B197C8`)

**Cache fields on the model:**

- `+32`: the previous frame's minimum distance;
- `+36`: this frame's running minimum;
- `+40`: the distance of the last size computation;
- `+44`: the frame number.

**First call of each frame:**

1. It compares **the distance of this first-drawn instance** with `+40`.
2. If the ratio is within a small tolerance of 1, it reuses the sizes cached in the materials (`+168/+172`).
3. Otherwise it recomputes them from min(previous frame's minimum, this distance) and stores that distance
   in `+40`.

**Later calls in the same frame** only update the running minimum.

### What the shared root model does

The root model is shared by about 20 instances. Two views draw it:

- the main view `7049F5D0`: instances at 18–300;
- view `7049D2C0`, the shadow/light view: always about 405 away.

**Pale runs (4 of 4).** The model's first frame is drawn by `7049D2C0` first.

1. The first computation uses distance 405.5, which gives a size of 15×16 → atlas proxy.
2. Every later frame, `7049D2C0` again draws first at about 405.5–408.
3. The ratio stays about 1, so the cache is never recomputed, although the root is 18–28 away.

**Normal runs (4 of 4).** The model's first frame is drawn only by the main view, and only far instances
(230–300).

1. The first computation gives about 23×25.
2. On the next frame `7049D2C0` draws first at 405.
3. 405 / 276 is far from 1, so the cache recomputes with min(18.6, 405) = 18.6. That gives 334×355, the full
   bark.
4. From then on the ratio 405 / 18.6 forces a recompute every frame.

Records: `size-history-excerpts.txt`, `stream-update-*-excerpt.txt` and `watch-normal-excerpt.txt`. In
normal runs the slot is patched 1–2 ms after the bark finishes loading, on the next frame's update.

### Why it varies

- The outcome depends on whether the shadow view's pass already sees the model in the model's first
  rendered frame. That depends on when the model and its instances finish streaming in, relative to that
  frame's passes. In pale runs the model object sits higher in memory (`0x42D84xxx` against
  `0x42D7xxxx`), so it loaded later.
- The race is between game threads, so host timing moves it:
  - with per-call history logging on the render thread, 0 of 16 runs were pale;
  - with the logging made cheap, 4 of 8 were pale.

### It heals when the camera moves

Spin sweeps with the trace on (`pr-sp1..10`): 2 of 10 started pale, with `7049D2C0` first. Both recomputed
within the spin (15×16 → 776×825 by about frame 630, after the turn started near frame 400). In play, the
pale state lasts only until the camera or hero moves far enough to change the first-drawn instance's
distance ratio.

## 4. Why this is not a recomp fault

- **The guest makes the choice.** The guest builds the fetch constants itself; the renderer draws exactly
  what the guest bound.
- **Every input is correct.** Texture contents, residency and the host texture cache are all fine.
- **The cause is the cache logic.** It compares the first-drawn instance's distance, not the minimum, which
  is a latent game bug. The trigger is a load-order race between game threads, which exists on the console
  too. Its odds there are unknown, since console timing cannot be measured here.
- **Not our pacing changes.** Turning off our loading-pacing changes (stream budget, worker-0 drain) does
  not remove it.
- **Nothing to restore.** No emulation fault was found to make "faithful" different from what runs now.

## 5. Opt-in fix: `FABLE2_FIX_LOD_SIZE_CACHE` (default off)

**The patch.** `src/core/hotfunc/gpu/LodSizeCacheFix.cpp` overrides `sub_82B197C8`.

- On, it runs a copy of the recompiler's literal output for that function (`fable_2_recomp.112.cpp`) with
  one line changed: `fdivs f3,f7,f5` → `fdivs f3,f30,f5`.
- The ratio test now divides f30 = min(previous frame's minimum, this distance), the distance the size
  computation uses, by the distance of the last computation.
- Off, it calls the original (`__imp__`).
- The game logs `[lod-size-cache] game texture-detail cache fix ON|off` once.
- The trace hook (`FABLE2_PALE_ROOT_TRACE`) wraps whichever of the two runs.

**Switch.**

- Env `FABLE2_FIX_LOD_SIZE_CACHE` (1 = on).
- Launcher setting `fixLodSizeCache` (CLI `--fix-lod-size-cache`). It sits in its own Fixes section,
  "Game bug fixes (changes original behaviour)", whose footer says these differ from the Xbox 360.
- The value is always passed explicitly by `LaunchSettings.settingsEnvironment`, so the Dev Launcher and
  the player app (`gameEnvironment`) both set it.
- Off is the default, because it changes what the original game does. Preservation-first.

**What it changes.**

- A model whose cache was filled from the shadow view gets its sizes recomputed on the next frame. That
  frame's minimum distance differs from the shadow view's ≈405, so the near root gets the full bark.
- In steady state the cache recomputes only when the minimum distance moves by more than the tolerance.
  The original recomputes every frame whenever the first-drawn instance's distance differs from the
  minimum, as it does at Bower Lake (405 vs 18.6).
- Both give the same sizes: they compute from the same minimum, view and scale. The fix only skips
  identical recomputations.

**Validation (2026-10-14, 2× Bower Lake still runs, no tracing, image classifier).**

| Check | Runs | Result |
|---|---|---|
| Fix on | `pr-fon1..16` | 0 of 16 pale. At the 25–31% rate seen with the fix off, 0 of 16 by chance is about 1% likely |
| Fix off | `pr-foff1..16` | 5 of 16 pale: the original behaviour is kept |
| Frame-matched parity, on vs off-normal | `pr-fon1,2` vs `pr-foff2,3` | **within-noise**: cross median 0.28 against floor median 0.28 / max 0.47 (`parity-on-vs-off.json`) |
| Town spin5, fix on | `pr-fon-town` | verdict ok, 0 blue frames; dark-frame flags 35/36 match the fix-off baseline `pr-foff-town` (37/63), a property of the scene |
| Old Tomb spin5, fix on | `pr-fon-tomb` | verdict ok, 0 blue frames |

All runs above had verdict ok.

**Not measured: perf.** The change removes some per-frame recomputations on the CPU (one cache check per
model per frame); no GPU work changes.

## Tooling added (trace-only, off by default)

- `FABLE2_SHADOW_TRACE` draw lines now carry per-fetch `m0x<mip address>/mip<min>-<max>/bias<n>` and
  `ib=0x<index base> n=<index count>` (`metal_command_processor.cc`).
- `src/core/hotfunc/gpu/PaleRootTrace.cpp` (`FABLE2_PALE_ROOT_TRACE=1`):
  - mesh-walker material dump, with `FABLE2_PALE_ROOT_COUNTS` (primitive counts, default 457);
  - slot/texref watcher with guest lr chains (`FABLE2_PALE_ROOT_WATCH=1`);
  - per-material streaming update log;
  - per-model size-cache history.
- Classifiers in the validation folder:
  - `paleclass.py`: image crop;
  - `traceclass.py`: root draw T0;
  - `runs.sh` / `runs1x.sh`: batch runners, 2 at a time.
