## CR-01: the SDK sleeps 100 ms on every overlapped content call

**Correction to the review.** The save container is not mounted through `XamContentCreateEx`: the
existing `__imp__XamContentCreateEx` trace never fires.

- `sub_82CBD9E0` resolves xam ordinal **0x271 (`XamContentCreateInternal`)** through
  `XexGetProcedureAddress` (`sub_82CBD7E0`) and calls it indirectly.
- The indirect call goes through the SDK's thunk, so `__imp__` overrides never see it.
- The GameThread then waits in `sub_82CBC558` (`MutexLock_WaitInfinite`) for the overlapped, while the
  SDK's dispatch thread sleeps 100 ms.
- The stack is `82CBC59C <824ED048 <824ECE20 <824EA7DC/824EA1A0`. Each such wait is followed at once by an
  open of `save:\chaptersave.bin`, `saveuid.bin` or `herosave.bin`.

**Fix** (`src/core/fable2_fast_content_io.h`, included from `src/core/fable2_skip_intro.h`):

- `__imp__XexGetProcedureAddress` forwards to the SDK. For ordinal 0x271, it then checks that the
  returned thunk's dispatch entry is the SDK's `XamContentCreateInternal`, and points that slot
  (`Memory::SetFunction`) at a wrapper.
- `__imp__XamEnumerate` and the existing `__imp__XamContentCreateEx` wrapper get the same fast path.
- **Fast path.** For an overlapped call:
  - run the SDK's own synchronous path (overlapped = 0), with the out-value pointed at the caller's
    pointer or at the overlapped length field;
  - then call `KernelState::CompleteOverlappedImmediateEx`, which sets result, extended error, length and
    context, signals the event, and queues the completion-routine APC exactly as the deferred path does;
  - return `ERROR_IO_PENDING` as before.
- Ordering: work and completion happen in call order, and the only change is that the sleep is gone.
  Guest registers are restored, and the 9th stack argument of `XamContentCreateEx` is put back.

**Proof:**

- `[fast-content] hooked XamContentCreateInternal thunk 832C2A3C`; each call completes in 0.06–0.11 ms.
- The three ~100 ms waits around Continue are gone from the `FABLE2_LOADING_TRACE` log.
- Title ready → load start fell from 0.62 to about 0.13 s. With the first content call fast, the
  following menu-transition wait (`8235DB34 <826C8898`) shrinks from 304 to about 22 ms.
- Continue → level-load fell from 1.12 to 0.85–0.96 s.
- **Save check.** An F5 quick save in a test session (`f5save.py`, target slot none) made the
  watcher log `saved`, with library entry `hero1-dog-live_2026-10-07_18-28-28`.
  - The session was `20261007-182809-521f4243`, on build 2, whose CR-01 code is the same as the final
    build.
  - The quick save went through the fast path: the fifth `[fast-content] XamContentCreateInternal`
    call.
  - It was repeated on build 3 (`20261007-183449-0972e6c0`, entry `_18-35-08`).
  - Nothing was written to a live slot.

**Left alone: `XamShowDeviceSelectorUI`.** It also costs ~100 ms just before the save mount: it is
headless in the SDK, which sleeps 100 ms before completing and 100 ms before `XN_SYS_UI = false`.

- A fast path for it was measured slower: the next wait (`8235DB34 <826C8898`) grew from about 22 to
  about 364 ms, and title → load start went from 0.13 to 0.37 s (build 3, `after3/`).
- The game appears to pace that transition on the `XN_SYS_UI` notifications, so the SDK path stays.

## CR-02: direct shared-memory writes validated after the copy

**Change** (`metal_shared_memory.cc`, `direct_write_run`): call `MakeRangeValid` before the copy, as the
staged path and the SDK's D3D12/Vulkan code do. A guest write that lands during the copy then faults,
invalidates the page, and is uploaded again.

**Mechanism counter** (trace-only, `FABLE2_DRAW_SKIP_TRACE=1`): after each direct write, compare the GPU
copy with guest RAM and count runs that differ while their pages are still marked valid. Over one traced
uncapped sweep each (32,768 direct-write runs):

- **23 stale-valid runs with the fix off** (`FABLE2_SHMEM_VALID_FIRST=0`, session `20261007-182201-8d8a77d7`);
- **0 with it on** (session `20261007-181739-77c10c8f`).

Frame time is unchanged.

## CR-03: VS 695413A9 computes tessellation factors

**What the draws do.** From the draw dump `out/validation/flash-20261007/dump-q_on.bin` (skip arm) and
`out/validation/cr-fixes-20261007/dump-cr03-on2.bin` (mode 1, frames 2600–2620):

- Each VS 695413A9 draw exports 30–36 32-bit values. The stream constant is c32–c35, and the bases run
  from 0x1B942040 to 0x1B967440, 1 KB apart.
- Those buffers are the **index stream of the tessellated draws of VS 5003700B7C9B1C16**: primitive type
  0x12 (patch range), no vertex buffers, about 110–500 draws per frame across 5 pixel shaders plus a
  depth-only variant.
- With the skip, all 10,529 consumers in 20 frames read the constant 1.0f (0x3F800000). With mode 1
  they read real per-patch values from 0.0 to 15.0: for example 0..15.0, 0.23..3.43, and 1.0.
- So these are adaptive **tessellation factors**. Without the pass, every patch is drawn at factor 1
  (coarse), and patches the game would cull (factor 0) are drawn anyway.
- In the idle Old Tomb view, the skip and mode-1 captures differ in only 10 pixels, so whatever surface
  it is barely shows here. It can matter in areas with more tessellated geometry; that was not checked.

**Fix:**

- Mode 1 (default) drops the user clip plane from these draws only: no PS, memexport VS, and a
  point/rect/quad list. With no colour output, the clip plane only trims depth-only coverage, and the
  export is what matters.
- The emulated pipeline then links: `materializeAll` failures 0, `ds_geomfail_vs695413A9` 0, about 39
  memexport draws per frame now submitted.
- If a pipeline still fails, it falls back to plain points.
- Mode 2 draws these as plain points without geometry emulation. Mode 0 is the old skip.

**Cost:**

- At uncapped frame rate, running these draws costs about 16% (164 → 136–138 FPS, p99 11.1 → 17 ms).
  The GPU Commands thread drops from 88 to 69% CPU, which means the run is GPU-bound: the GPU now
  tessellates for real.
- Mode 2 costs the same (138.7 FPS). Turning off memexport readback and preserve does not help either
  (138.6 FPS).
- **At 60 FPS capped (normal play) it costs nothing:** p99 18.46 against 18.45 ms, 60.0 FPS presented,
  0 gaps.

**Chosen default: mode 1.** It is correct, since the consumers get real tessellation factors rather than
stale 1.0, and free at 60 FPS. Mode 2 is no cheaper and has undefined point size. Use `=0` to get the
uncapped headroom back.

**Visual check.** Sweep montages and dark-flash detection show no new artifact. The pink motes are in the
baseline too. Files: `baseline/overview-sweep.png`, `after/overview-sweep.png`.

## CR-05: the binary archive kept retrying a poisoned save

**Finding first.**

- All 22 fragment-less pipelines of a normal warm-up serialize fine. They are already in older segments
  (warm-up "hits 372"), and a cold run that adds them saves fine.
- A fragment-less copy of a coloured pipeline also saves fine (`FABLE2_ARCHIVE_TEST_NOFRAG=1`, a one-off A/B hook removed 2026-10-08, with the
  fix off: `cr05/off1`).
- So "expecting 'fragment' stage" needs something narrower that today's caches do not trigger.
- Skipping every fragment-less pipeline (an earlier draft, now mode 2) only adds 22 misses to the next
  launch after a cold cache (`cr05/on1-next`). It is not the default.

**Change** (`metal_pipeline_cache.cc`, mode 1, the default):

- When a save fails, replace the in-memory archive with a fresh one at the next segment index (never
  `.full`), instead of setting `dirty` and failing again every 30 s.
- If an earlier save of the failed segment succeeded, its file stays.
- New pipelines are persisted again. The failed segment's unsaved pipelines compile once on the next
  launch.

**Proof** (trace-only `FABLE2_ARCHIVE_TEST_FAIL_SAVE=1` makes every save of the first archive fail):

- **Fix off** (`cr05fail_off`, `20261007-183901`): the save fails at warm-up and again at +30 s, every
  time.
- **Fix on**, cold archive with new in-game pipelines (`cr05fail_on_poison`, `20261007-184138`):
  - the save fails once, then logs `new pipelines now go to …seg000002`;
  - at +30 s it logs `saved 3462576 bytes`;
  - the next launch (`20261007-184228`) loads that segment with 129 hits.
- With today's normal caches, the real failure did not occur in any run: 0 "expecting 'fragment'"
  lines, and archive saves succeeded whenever needed.

**Separate finding, not fixed.** Pipelines compiled in the last 30 s before a session closes are never
saved: the close path doesn't serialize. After a 20 s session the next launch had 18 misses
(`baseline/poison-next`). This is the same class as pattern 7.

## CR-08: every guest `mfmsr`/`mtmsrd` took the global recursive mutex

**What the sections contain.** `tools/apply_recomp_patches.py` (`apply_fast_msr`) checks every path from
each `REX_ENTER_GLOBAL_LOCK()` to its leave.

- **All 8,406** sections hold only a reservation pair plus register instructions:
  - `lwarx addi stwcx.` (8,046)
  - `lwarx add stwcx.` (314)
  - `lwarx cmpw bne stwcx.` (25)
  - `lwarx stwcx.` (14)
  - `ldarx cmpd bne stdcx.` (7)
- Those enters become `FABLE2_MSR_ENTER_ATOMIC()`, marked `// [recomp-patch: fast-msr]`.
- Any section with another load or store, a call, a return or nesting would keep the mutex. None exists
  today.
- The patch is idempotent: a second run marks 0.

**Why it is safe without the mutex:**

1. **The reservation pair is a real host CAS.** SDK `codegen/builders/helpers.h:277-318`:
   - `lwarx`/`ldarx` load the raw big-endian word into `ctx.reserved`;
   - `stwcx.`/`stdcx.` emit `__sync_bool_compare_and_swap(REX_RAW_ADDR(ea), ctx.reserved,
     bswap(rS))`, an atomic compare-exchange on the guest address against the reserved value, and a
     full barrier.
   - All 8,436 `stwcx.`/`stdcx.` sites in the generated code are this CAS.
   - `lwarx` is an aligned 32/64-bit load, which is single-copy atomic on ARM64. A stale read only makes
     the CAS fail and retry.
   - The seq_cst fences emitted around `mfmsr`/`mtmsrd` stay.
2. **Each section's new value depends only on the old value of that word.** So the CAS is
   linearizable on its own, and value-CAS ABA cannot matter. No section chases a pointer.
3. **No other path to these words relies on the mutex:**
   - HLE spinlocks (`xeKeKfAcquireSpinLock`, `KeTryToAcquireSpinLockAtRaisedIrql`) use
     `atomic_cas`/`atomic_store_release` (`xboxkrnl_threading.cpp:967-985, 1064`).
   - `RtlEnter/TryEnter/LeaveCriticalSection` use `atomic_cas`/`atomic_inc`/`atomic_dec`
     (`xboxkrnl_rtl.cpp:379-445`).
   - The `Interlocked*SList` functions use a 64-bit `atomic_cas`.
   - The guest's own releases, such as the pool `stw 0` after `SpinLock_Acquire_822D7408`, are plain
     stores outside any section.
   - The SDK's kernel takes `global_critical_region` only for DPC lists, module bookkeeping and the
     media player app.
   - Interrupt dispatch (`ExecuteInterrupt`) holds the mutex, but an interrupt cannot observe a torn CAS,
     and on hardware an interrupt may run right after such a section anyway.
4. **`mfmsr` reads a per-host-thread depth.** Under the old mutex, `REX_CHECK_GLOBAL_LOCK` could only
   ever see the reading thread's own depth, so the result is the same.
   - A per-thread bitmask records which sections took the mutex, so a leave unlocks only those.
   - Sections nested more than 64 deep always lock.
   - With the switch off, every macro is the generated original (`src/core/fable2_guest_memory.h`).

A live AV/hang check cannot prove atomicity, since such races are rare. The argument above is the
evidence. Live runs: 0 AVs in 41 sessions.

**Mechanism.** `/usr/bin/sample` for 3 s from t = 4 s (level load and loading frames), `cr08/`. Timing is
distorted under sampling; only the shares are meaningful.

| Thread | `std::recursive_mutex::lock` (inclusive) | `__psynch_mutexwait` | `SpinLock_Acquire_822D7408` (inclusive) |
|---|---|---|---|
| GameThread, fix off → on | 5.0% → 0.5% | 4.1% → 0.5% | 0.9% → 0.7% |
| 3D Engine, fix off → on | 9.6% → ~0 | 8.4% → ~0 | 3.6% → < 0.2% |

**Wall-time effect: small.**

- Load-window CPU: GameThread 2.37 → 2.21–2.30 s, 3D Engine 3.71 → 3.58–3.70 s.
- The level-load call is unchanged (0.76–0.79 s).
- The sweep with `FABLE2_FAST_MSR=0` matches all-on (137.5 vs 136 FPS).
- The 10–14% spinlock share from the 2026-10-06 profile was measured before the checkpoint `getenv`
  fix, which removed most of that contention.
