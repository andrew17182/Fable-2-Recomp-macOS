## 2. Changes: `FABLE2_DRAW_PREP_LITE2` (default on, `=0` restores each)

All are exact: the same draws, state, bindings and order are encoded; only host-side bookkeeping changed.

1. **Load check reused, guarded by a state snapshot.**
   - `IssueDrawImpl` takes `TextureCache::GetLoadCheckState()` right before `MayRequestTexturesLoadData` and passes
     both to `MetalTextureCache::RequestTexturesWithLoadHint`.
   - The snapshot is a new `load_check_epoch_`, plus the scaled-resolve generation and `texture_bindings_in_sync_`.
     The epoch is bumped after anything that can change the check's answer for unchanged registers:
     - every watch callback (any thread, after it sets the outdated flag);
     - every `textures_` insert, erase or clear;
     - `ResetTextureBindings` (also run by `BeginFrame` inside `EnsureCommandBuffer`, between the check and the request).
   - If the snapshot is unchanged, the earlier answer is what a second check would return. A callback after the
     comparison is the same interleaving as one after the original's second check. If it changed, the check runs
     again, as before (~0.2–0.4% of draws).
   - `FABLE2_DRAW_PREP_LITE2_VERIFY=1` recomputes on every reuse: **0 mismatches** (town 2× spin, Bower 2× spin,
     area transition at 2×; 2.1 M reuses in the area run).
2. **Texture find memo** (SDK patch). It is a 1024-entry direct-mapped host key → `Texture*` table, with positive
   results only. Any erase or clear of `textures_` bumps `textures_generation_` and so invalidates every entry.
   It is used by `MayRequestTexturesLoadData` and `FindOrCreateTexture`.
   - 98% hits. `FABLE2_TEX_KEY_MEMO_VERIFY=1` also checks every hit against `textures_.find`: **0 mismatches** in
     19 M lookups (area transition at 2×).
   - The host-key memo now looks up before the virtual `IsScaledResolveSupportedForFormat` call. Entries exist only
     for supported formats (a pure function of the key), so a hit implies support.
3. **Pending-write list rebuilt in reused storage.** `RetireFenceWaitedSharedMemoryWrites` keeps the same 64-entry
   limit and overflow rule. It builds into a member vector and swaps it in, so there is no 2 KB stack fill and no
   copy back.
4. **Float constants packed by runs**: one `memcpy` per run of consecutive used constants, with inline `ctz`. It
   writes the same bytes in the same order and stops at the same buffer end.
5. **No double fill, no copy of constant payloads.** The scratch is not zero-filled when every writer fills all of it
   (logical size ≥ 16). The cache-hit path swaps the scratch into `current_payload` instead of copying it. The
   descriptor-indices payload uses reused storage instead of a new vector per upload.
6. **Cached texture properties.** `MetalTexture` caches `mipmapLevelCount`, `pixelFormat` and `textureType` in its
   constructor and refreshes them where tex-rename swaps the backing (`RenameBacking`, `SwapBackingForVerify`).
7. **Flat residency set.** `residency_set_resources_` (insert, count and clear only) is a `FlatPtrSet` instead of
   `std::unordered_set`.
8. **Sampler parameter memo.** `GetSamplerParameters` is a pure function of the six fetch constant dwords, the
   binding's four requested filters and the `anisotropic_override` cvar. It is memoized by all of them in a
   256-entry direct-mapped table.

Pre-existing behaviour found while verifying: `MayRequestTexturesLoadData` sometimes answers "no load" while
`RequestTextures` then loads a texture (43 per town 2× spin, 92 per area run). The original asserts this never
happens (`assert_zero`, compiled out in release); those loads run outside the upload batch, the same as before.
With the switch they are counted: the `[draw-prep-lite2] load check reused … loads outside the batch N` log line.
The cause was not investigated (it is not related to this change).

Build note: the SDK part is in `backends/metal/sdk-metal-gpucmd.patch` (regenerate with `regen-patch.sh`). It
has no shader hunks, so the agent shader-cache key is unchanged.

## 4. Moving work off the thread (design note; not built)

After this round the thread's time in town 2× is roughly:
- 50% draw preparation (state, textures, constants, hazard ranges);
- 25% encoding prepared draws (driver calls, resource usage, encoder state);
- 10% packet and register processing;
- 5% each for uploads, resolves and render-pass setup.

The remaining items above 1% are each small. The profile shows a structural split, not one hotspot.

**Encoder worker** (the only split with a large payoff):
- Prepared draws are already self-contained records in a queue (`FlushPreparedDrawQueue` → `EncodePreparedDraw`).
  A worker thread could encode a flushed batch while the command processor prepares the next one. That would take
  up to ~25% off this thread: ~2.5 ms/frame on the M5 Max town 2×, about 4–5 ms on a base M1.
- What it needs:
  - every other encoder use on the command processor thread must either go through the same ordered stream or
    wait for the worker to drain first: pass begin/end, texture upload blits and the pre-commit encoder, resolves
    and transfers, compute dispatches, fences, `useResource` and residency;
  - state that encoding reads and writes needs one owner: the per-encoder resource usage tables, the pending
    shared-memory writes and fences, bindless heap entries, and telemetry;
  - a drain point before every submission and readback.
- With a "drain before any non-draw encoder use" barrier, the gain depends on how many draws each flush holds.
  Measure the flush count and draws per flush first: if passes break every few draws, the barriers eat the gain.
- This is not contained (it touches pass management, uploads, resolves and hazard tracking), so it was not built.

**Not worth it:**
- *Parallel render encoders* (`MTLParallelRenderCommandEncoder`): only the encode quarter is parallel, and draws
  within a pass keep their order. It needs the same ownership work as the worker.
- *A constant-packing worker*: `PrepareDrawConstants` (17%) produces the buffer offsets the draw record needs right
  away, so a worker would have to hand back futures. It saves less than the encoder worker for similar
  synchronisation.
